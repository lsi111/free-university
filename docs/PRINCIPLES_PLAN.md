# 원리 깊이 읽기 추가 계획 (번역 작업이 끝난 뒤 이어서 한다)

## 왜 하는가
- 지금 교시는 `설명 → 예 → 확인 문항` 구조라서 문항을 통과하는 데 맞춰진 느낌이 있다.
- 대학은 원리를 배우는 곳이다. "어떻게 푸는가"뿐 아니라 "왜 그렇게 되는가, 어디서 깨지는가"를 읽을 자리가 필요하다.
- 기존 설명·문항·정답은 건드리지 않고, 교시마다 **원리 깊이 읽기**를 더한다.

## 선행 조건
1. 영어·스페인어 번역 완료: `node tools/i18n.mjs status`에서 두 언어 모두 51/51.
2. 완료 후 `npm test`, `npm run check` 통과, 배포(Vercel·Cloudflare)까지 마친 상태에서 시작한다.
   - 번역이 끝나기 전에 한국어 원본의 `explain` 배열 길이를 바꾸면 번역 덧씌움이 어긋나므로 `explain`은 건드리지 않는다. 새 필드로만 더한다.

## 설계

### 데이터: 교시에 선택 필드 두 개 추가 (기존 데이터는 그대로 유효)
```json
{
  "deep": [ "문단", "- 목록", { "figure": "...", "alt": "..." } ],
  "ponder": [ "스스로 물어볼 질문 1", "질문 2" ]
}
```
- `deep`: 원리 깊이 읽기. 문단·목록·그림 블록(기존 `explain`과 같은 형식).
- `ponder`: 채점하지 않는 생각해 볼 질문 2~3개. 답은 쓰지 않아도 된다.
- 둘 다 없어도 통과(점진적 확장). 있으면 규칙을 검사한다.

### 쓰는 방법 (`deep` 5~7문단, 한국어 1,200~2,000자)
1. **문제의식**: 이 개념이 어떤 곤란을 풀려고 나왔는가.
2. **왜 그런가**: 공식·규칙의 근거. 유도, 증명 스케치, 인과 구조, 논증의 뼈대.
3. **직관과 반례**: 흔한 오개념, 겉보기엔 맞지만 틀린 경우.
4. **가정과 한계**: 어떤 가정 위에서 성립하는가, 언제 깨지는가.
5. **연결**: 앞 교시·다른 학과 개념과의 이어짐(학과 간 연결 기능과 같은 **굵은 용어** 사용).
6. 규칙은 `docs/AUTHORING.md`와 같다: 사례·인물·조직은 허구, 실제 저작 인용 없음, 의료·법률·투자 조언 없음, 역사·인명은 확실한 것만 일반적으로, 논쟁적인 주제는 입장을 균형 있게.
7. 문항 정답을 새로 노출하지 않는다. 문항에 없는 새 계산·공식을 요구하지 않는다.

### 화면
- 교시 화면에서 `설명`과 `예` 사이(또는 뒤)에 접히는 섹션 "원리 깊이 읽기"를 둔다. 기본은 펼침으로 시작해 느낌을 보고 정한다.
- `ponder`는 섹션 끝에 "생각해 보기"로 표시한다.
- 검색(`engine/search.js`)이 `deep`·`ponder`도 색인한다.
- 진도에는 영향 없음(읽기만으로 이수 조건이 바뀌지 않는다). 시험 느낌을 더 줄이려면 별도 결정: 문항 통과 전에도 다음 교시를 열 수 있는 "열람 모드"는 이번 범위 밖, 시험 느낌이 남으면 다음 과제로.

### 번역
- `src/engine/i18n.js`의 `sourceOf`/`applyDeptOverlay`가 `deep`·`ponder`를 다루도록 확장(길이가 어긋나면 해당 부분만 한국어로 폴백).
- `tools/i18n.mjs`의 `prep/build/verify`는 새 필드를 자동으로 포함한다. 한국어 `deep`를 쓴 학과부터 다시 `prep` → 번역 → `build`.

## 작업 순서

### 1단계 엔진·화면 (직접, 에이전트 불필요)
- `schema.js`: `deep`(문자열/그림 블록 배열)·`ponder`(문자열 배열) 선택 검증, `collectFigures`에 `deep` 그림 포함.
- `views/lesson.js`: 섹션 렌더링, `features` 자동 판정(`$...$`가 있으면 `formula`)은 `tools/merge-stages.mjs` 방식으로.
- `search.js`, `i18n.js`(엔진), `tools/i18n.mjs`, `tools/check.mjs`("원리 깊이 읽기" 절: 있으면 5~7문단·1,000자 이상·ponder 2~3개), 테스트 추가.
- UI 문구는 `content/i18n/{en,es}/ui.json`에 추가.

### 2단계 시범 3개 학과 (사용자 확인)
- 수학(`mathematics`, 자연), 경제학(`economics`, 사회), 철학(`philosophy`, 인문) × 교시 20개 = 60교시.
- 학과당 에이전트 1개가 `deep`·`ponder`를 써서 `tools/merge-deep.mjs`(만들 것: `merge-stages.mjs`와 같은 방식, 교시 id별 필드만 병합)로 반영 → `validate-dept` 통과.
- 사용자가 화면에서 읽어 보고 분량·깊이·말투를 정한다. 여기서 규칙을 확정한다.

### 3단계 전체 확대
- 나머지 48개 학과를 6~8개씩 묶어 병렬 실행(에이전트 1개 = 학과 1개 = 교시 20개), 묶음마다 `npm test`/`npm run check` 후 커밋·푸시.
- 한도에 걸리면 `Workflow`의 `resumeFromRunId`로 이어간다. 학과 하나의 일은 한 에이전트에서 끝나야 하므로 재시도 단위는 학과.
- 모델: 원리 설명은 정확성이 중요하므로 기본 모델. 커밋 단계만 Haiku.

### 4단계 번역
- 학과별로 영어·스페인어 `prep → 번역 → build`(번역 도구가 새 필드를 이미 포함).
- 비용이 크므로 한국어 완료 학과부터 순서대로 하고, 번역이 없는 필드는 한국어로 보이게 둔다(기능 손실 없음).

### 5단계 마무리
- `README.md` 현재 상태, `docs/AUTHORING.md`에 `deep`/`ponder` 절 추가.
- `npm test`, `npm run check`, 브라우저에서 ko/en/es 확인, 두 곳에 재배포, 커밋·푸시.

## 규모 어림
- 한국어 `deep` 약 1,020교시 × 1,600자 ≈ 160만 자. 이번 번역(2개 언어)보다 작업량이 작지만, 영어·스페인어까지 합치면 번역과 비슷한 규모가 한 번 더 든다.
- 그래서 2단계(시범)에서 분량을 먼저 확정한다. 교시당 800자로 줄이면 전체 비용이 절반이 된다.

## 결정이 필요한 것
- 시범 학과 3개를 위 3개로 할지.
- `deep`을 기본 펼침으로 할지, 접어 둘지.
- 문항 통과와 상관없이 다음 교시를 열람할 수 있게 하는 "열람 모드"를 따로 할지.
